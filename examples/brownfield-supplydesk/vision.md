# Vision: SupplyDesk 팀 월 예산 한도

## Summary

SupplyDesk는 직원이 비품을 신청하고 팀장이 승인하면 승인 건이 매일 밤 ERP로 전송되는 사내 비품 신청 API이다.
지금은 팀의 비품 지출을 신청 단계에서 제한하는 장치가 없어, 재무팀이 정한 월 예산을 넘는 신청도 그대로 접수된다.
이번 작업은 팀마다 월 예산 한도를 두고, 신청 시점에 이번 달 승인·대기 금액 합계가 한도를 넘으면 신청을 거부하고 남은 금액을 알려 주는 기능을 추가한다.
기대 결과는 예산을 넘는 신청이 접수 단계에서 0건으로 차단되고, 팀장이 자기 팀의 이번 달 예산 잔액을 API로 확인할 수 있는 것이다.

## Target Users

| User Type | Description | Primary Need |
|-----------|-------------|--------------|
| 직원 (employee) | 비품을 신청하는 임직원 | 신청이 거부되면 이유(예산 초과)와 남은 금액을 바로 알고 싶다 |
| 팀장 (manager) | 자기 팀 신청을 승인·반려하는 관리자 | 이번 달 팀 예산 한도, 사용액, 잔액을 한 번에 조회하고 싶다 |
| 재무팀 | 팀별 월 예산을 정하는 부서 | 정한 예산이 신청 단계에서 그대로 적용되어야 한다 (이번 작업에서는 SQL 시드로 입력) |

## Success Criteria

- [ ] 예산이 거의 찬 팀의 직원이 `POST /requests`를 보내면, 신청 행이 생성되지 않고 "예산 초과" 오류와 남은 금액이 응답에 포함된다.
- [ ] 한도 안의 신청은 기존과 동일하게 201로 생성되고 응답 형식이 바뀌지 않는다.
- [ ] 팀장이 잔액 조회 API를 호출하면 이번 달(한국 시간 1일~말일) 한도, 사용액(승인 + 대기 합계), 잔액이 나온다.
- [ ] 기존 테스트가 모두 통과하고, 한도 검사에 대한 자동 테스트가 추가되어 통과한다.

## In Scope (First Release)

| Feature | Description | Why it cannot wait |
|---------|-------------|--------------------|
| 팀별 월 예산 저장 | 팀 ID와 월별 예산 한도를 저장하는 테이블을 새 마이그레이션으로 추가하고, 데모용 예산은 SQL 시드로 넣는다 | 한도 검사의 기준 데이터가 없으면 아무것도 동작하지 않는다 |
| 신청 시 한도 검사 | 신청 금액(신청 시점의 비품 단가 × 수량)과 이번 달(KST) `approved` + `pending` 건 합계를 더해 한도를 넘으면 신청을 거부하고 남은 금액을 응답한다 | 성공 기준의 데모 장면 그 자체 |
| 팀장 예산 잔액 조회 | 팀장이 자기 팀의 이번 달 한도, 사용액, 잔액을 조회하는 API | 한도 검사 결과를 사람이 확인할 수 있는 유일한 창구 |

## Out of Scope

| Feature | Why it can wait |
|---------|-----------------|
| 예산 설정 API와 재무팀용 관리자 웹 화면 | 현재 시스템은 API 전용이고 재무팀 역할도 없다. 데모는 SQL 시드로 충분하다 |
| 한도 80% 도달 시 슬랙 알림 | 외부 연동이며 핵심 흐름(거부와 잔액 조회)에 영향이 없다 |
| 월말 예산 리포트 엑셀 다운로드 | 보고서 설계와 외부 라이브러리가 필요한 별도 작업이다 |
| 단가 변경 이력 반영 | 신청 시점 단가로 계산하면 되고, 이후 단가 변경은 이번 범위에서 고려하지 않는다 |

## Current State

SupplyDesk 1.4.2는 비품 카탈로그 조회, 비품 신청, 내 신청 목록 조회, 팀장의 승인·반려 다섯 개 API를 제공한다. 사내 게이트웨이가 넣어 주는 헤더로 직원 ID, 역할(employee/manager), 팀 ID를 식별하며 별도 로그인은 없다. 승인·반려는 팀장만, 자기 팀 건만, 대기 중인 건만 가능하다. 승인된 신청은 재무팀 소유의 야간 배치가 읽어 ERP로 전송하고 전송 시각을 기록한다. 예산 개념은 아직 없다.

## Must Not Change

- `src/legacy/erp/**` — 재무팀 소유 ERP 전송 모듈. 어떤 수정도 금지
- `requests.status` 값 집합(`pending` / `approved` / `rejected`)과 의미, `erp_sent_at` 컬럼 의미 — ERP 야간 배치가 `status = 'approved' AND erp_sent_at IS NULL` 행을 읽어 가므로 새 상태값 추가나 의미 변경은 재무팀 배치를 깨뜨린다. 예산 초과 거부는 신청 행을 만들지 않고 오류 응답으로만 처리한다
- 마이그레이션 `001`, `002` 파일 — 이미 운영 DB에 적용됨. 스키마 변경은 새 번호의 마이그레이션 파일로만 추가한다
- `src/middleware/auth.ts`와 게이트웨이 헤더 계약(`X-Employee-Id`, `X-Employee-Role`, `X-Team-Id`) — 새 역할 추가 금지
- 기존 5개 API의 경로, 요청 형식, 성공 응답 형식 (`POST /requests` 성공 응답 포함)

## Open Questions

- [ ] 어느 팀에도 예산이 설정되지 않은 경우 신청을 허용할 것인가(한도 없음으로 간주), 아니면 거부할 것인가?
- [ ] 예산 초과 거부 응답의 HTTP 상태 코드는 무엇으로 할 것인가? (예: 409 또는 422; 기존 코드는 `{ error: "코드" }` 형식을 쓴다)
