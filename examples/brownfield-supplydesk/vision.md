# Vision: SupplyDesk 팀 예산 한도

## Summary

SupplyDesk는 직원이 비품을 신청하고 팀장이 승인하면 승인 건이 매일 밤 ERP로 전송되는
사내 비품 신청 API다. 지금은 팀이 한 달에 얼마를 신청하든 막는 장치가 없어, 재무팀이
사후에 초과 지출을 발견한다. 이번 작업은 팀별 월 예산(한국 시간 기준 1일~말일)을 두고,
비품 신청 시점에 이번 달 승인+대기 금액 합계가 한도를 넘으면 신청을 거부하고 남은
금액을 알려 주는 기능을 추가한다. 예산은 재무팀이 정하며, 이번 릴리스에서는 시드
스크립트로 직접 입력한다. 기존 신청·승인·ERP 전송 흐름은 그대로 유지한다.

## Target Users

| 역할 | 핵심 필요 |
|---|---|
| 직원 | 비품을 신청할 때 예산 때문에 거부되면 그 이유와 남은 금액을 바로 알고 싶다 |
| 팀장 | 자기 팀의 이번 달 예산 한도와 남은 금액을 확인하고 싶다 |
| 재무팀 | 팀별 월 예산을 정하고, 한도를 넘는 신청이 접수되지 않게 하고 싶다 |

## Success Criteria

- [ ] 예산이 거의 찬 팀의 직원이 비품을 신청하면 "예산 초과"로 거부되고, 응답에 남은 금액이 포함된다
- [ ] 같은 신청을 예산이 남은 팀의 직원이 하면 기존처럼 접수된다(대기 상태)
- [ ] 이번 달 합계는 한국 시간 1일 00:00부터 말일 23:59:59까지의 승인+대기 건만 포함하고, 반려 건과 지난달 건은 제외한다. 합계가 한도와 정확히 같으면 접수하고, 한도를 넘을 때만 거부한다
- [ ] 팀장이 자기 팀의 이번 달 한도·사용액·남은 금액을 조회할 수 있다
- [ ] 기존 테스트가 모두 통과하고, 기존 5개 API의 요청/응답 형식이 바뀌지 않는다

## In Scope (First Release)

| 기능 | 설명 | 왜 지금 필요한가 |
|---|---|---|
| 팀별 월 예산 저장 | 팀·월·한도 금액을 저장하는 새 저장 구조. 초기 데이터는 시드 스크립트로 입력 | 한도 검사의 기준 데이터 |
| 신청 시 예산 한도 검사 | 신청 시 이번 달(KST) 승인+대기 금액 합계 + (단가 × 수량)이 한도를 넘으면 거부 | 이번 작업의 핵심. 데모 장면 |
| 예산 초과 응답 | 거부 시 오류 코드와 남은 금액을 응답에 포함. 기존 응답 형식에 오류 코드 하나를 추가하는 것으로 한정 | 직원이 거부 이유를 바로 알아야 함 |
| 팀장 잔액 조회 | 팀장이 자기 팀의 이번 달 한도·사용액·남은 금액을 조회하는 읽기 전용 API 1개 | 데모에서 남은 금액을 미리 보여 줄 수 있고, 읽기 전용이라 위험이 낮음 |

## Out of Scope

| 기능 | 왜 미뤄도 되는가 |
|---|---|
| 재무팀용 예산 관리 웹 화면 | 화면 작업은 하루 범위를 넘음. 이번엔 시드 스크립트로 대체 |
| 팀장의 예산 설정/변경 API | 예산은 재무팀 권한. 팀장이 바꾸면 안 되므로 만들지 않음 |
| 80% 소진 시 슬랙 알림 | 외부 연동. 핵심 흐름이 동작한 뒤 다음 단계 |
| 월말 엑셀 리포트 | 배치와 파일 생성. 다음 단계 |
| 예산 이월, 추가 예산 승인 등 예외 처리 | 재무 정책 확정이 먼저 필요 |

## Current State

SupplyDesk 1.4.2는 비품 카탈로그 조회, 비품 신청, 내 신청 목록, 팀장 승인/반려의 5개
API를 제공한다. 인증은 사내 게이트웨이가 넣어 주는 직원 ID·역할·팀 ID 헤더를 읽어 처리하며,
승인/반려는 팀장만, 자기 팀 건만, 대기 상태인 건만 가능하다. 신청은 `pending` → `approved`
또는 `rejected`로 바뀌고, 재무팀의 ERP 야간 배치가 `status = 'approved'`이면서 `erp_sent_at`이
비어 있는 행을 읽어 전송한다. 현재 예산 개념은 없고, 신청 시점의 단가도 저장하지 않는다
(비품 카탈로그의 현재 단가만 있음).

## Must Not Change

- `src/legacy/erp/**`: 재무팀 소유. 파일 내용, 의존성, 호출 방식 모두 변경 금지
- `requests.status`의 값 집합(`pending` / `approved` / `rejected`): ERP 야간 배치가
  `status = 'approved' AND erp_sent_at IS NULL`을 읽는다. 값을 바꾸거나 새 상태를 추가하면 배치가 깨진다.
  예산 거부는 새 상태가 아니라 **신청 자체를 접수하지 않는 것**으로 구현한다
- `migrations/001_init.sql`, `migrations/002_erp_sent.sql`과 `requests`, `items` 테이블의 기존 컬럼:
  운영 DB에 이미 적용됨. 변경·삭제 금지. 새 마이그레이션 파일로 테이블이나 컬럼을 **추가**하는 것만 허용
- 기존 5개 API(`GET /items`, `POST /requests`, `GET /requests/mine`, `POST /requests/:id/approve`,
  `POST /requests/:id/reject`)의 요청/응답 형식: 기존 클라이언트가 의존. `POST /requests`에
  예산 초과 오류 코드 하나를 추가하는 것만 허용
- `src/middleware/auth.ts`와 게이트웨이 헤더 계약(`X-Employee-Id`, `X-Employee-Role`, `X-Team-Id`): 변경 금지

   금액이 달라진다. (a) 새 마이그레이션으로 `requests`에 단가 컬럼을 추가해 신청 시점 값을 저장,
   (b) 조회 시 카탈로그 현재 단가를 조인. 워크샵 당일 결정
2. **예산이 등록되지 않은 팀의 신청**: 해당 월 예산 행이 없는 팀은 (a) 제한 없이 접수, (b) 모두 거부.
   재무팀 의도 확인 필요
